## 1. Scoping an audit (goals, access, path A/B/C)

- Google on what an audit should deliver: "If your SEO offers to do an SEO audit for you, be sure to carefully consider what's involved and only grant read access to Search Console (at this stage, don't grant them write access). An SEO audit should be about giving you realistic estimates of improvement, and an estimate of the work involved. If they guarantee you that their changes will give you first place in search results, find someone else." — https://developers.google.com/search/docs/fundamentals/do-i-need-seo (2026-06-05) — **Documented**. **Use this as the course's definition of a good audit deliverable**: realistic estimates of improvement + an estimate of work = Value and Effort columns.
- Google on communication (useful as audit "ground rules"): "How can I expect to communicate with you? Will you share with me all the changes you make to my site, and provide detailed information about your recommendations and the reasoning behind them?" — same page — **Documented**.
- Google on discovery questions an SEO should ask: "Your SEO should ask questions about what makes your business unique, who your competitors are, how search results can help, and how your customers find you." — same page — **Documented**. Good scoping-call checklist (tie to M01.L01 goal, M10 competitors).
- Search Console roles (for path C access): "Owner: Has full control over properties in Search Console. Owners can add and remove other users, configure settings, view all data, and use all tools." / "Full user: Has view rights to all data and can take some actions." / "Restricted user: Has simple view rights on most data." — https://support.google.com/webmasters/answer/7687615 — **Documented**.
  - The permissions table lists **Change of Address** with "View only" for both Full and Restricted users (table icons, read from the page text: "Change of Address|View only|View only") — so **only an owner can submit a Change of Address**. **Documented** (inferred from the table layout; confirm in a browser before quoting the exact cell).
  - "Full/restricted/associate users: A property can have a maximum of 100 non-owners." — same — **Documented**.
  - **Teaching point:** for path C, an audit needs only **Restricted** (or Full) access, which matches Google's "only grant read access". Fixes and a Change of Address need the owner. M08.L01 already noted restricted users can't add annotations.
- **Path A/B/C** (course outline §12): A = own site; B = Blogger practice site + WordPress practice site (Local/Playground or hosting); C = friend's/client's site "who gives written permission and Search Console/GA4 access". "Low traffic is expected and fine. The rubric grades method and evidence, not traffic numbers." Path B learners auditing Local/Playground won't have Search Console data for the WordPress copy: the audit can use the Blogger property for GSC steps and a Screaming Frog crawl of the local site. — course rule, not a source.
- Scope statement contents (**Observed practice**, course synthesis): goal and KPI (from M01.L01/M08.L06), site and properties in scope (all host variants), access granted (GSC role, GA4 role, CMS role), date range and baseline, what's out of scope (e.g. paid search, full content rewrite), tools (free only), deliverables (report, tickets, 90-day plan, dashboard, walkthrough), and timeline. No primary source prescribes this list; present it as the course template.
- Screaming Frog on migrations, also true of audits: "It's important to have a shared scope and strategy as well as a process and checklist in place to mitigate any issues in ranking." — https://www.screamingfrog.co.uk/seo-spider/tutorials/how-to-use-the-seo-spider-in-a-site-migration/ — **Observed practice** (vendor tutorial).

## 2. The audit order (and why indexing comes first)

- Google's minimum bar, which justifies starting with indexing and status: "As long as your page meets the minimum technical requirements, it's eligible to be indexed by Google Search: Googlebot isn't blocked. The page works, meaning that Google receives an HTTP 200 (success) status code. The page has indexable content." Also: "Just because a page meets these requirements doesn't mean that a page will be indexed; indexing isn't guaranteed." — https://developers.google.com/search/docs/essentials/technical (2025-12-18) — **Documented**.
- "The technical requirements cover the bare minimum that Google Search needs from a web page in order to show it in search results. There are actually very few technical things you need to do to a web page; most sites pass the technical requirements without even realizing it." — https://developers.google.com/search/docs/essentials (2025-12-10) — **Documented**. Good counterweight to "200 issues": most small sites pass the basics.
- Search Essentials has three parts: "Technical requirements: What Google needs from a web page to show it in Google Search." / "Spam policies: The behaviors and tactics that can lead to lower ranking or being completely omitted from Google Search results." / "Key best practices: The main things that can help improve how your site appears in Google Search results." — same — **Documented**. The course's audit order maps onto this: technical requirements (steps 1–2) → best practices (3–8) → spam policies (9).
- **Google does not publish an audit order.** The 9-step order in the outline is a **course rule** (it follows the crawl → index → rank logic and non-negotiable #7 "Indexable before optimised"). Label it that way in the lesson.
- Practitioner example of an audit sequence (Ahrefs blog, Chris Haines, updated 2026-08-12): its 13 steps start "1. Run a crawl of your website", "2. Identify organic traffic drops and work out what caused them", "3. Check for any duplicates of your website", "4. Find and diagnose indexability issues", then mobile, Core Web Vitals, broken pages, sitemap, on-page, declining content, competitor keywords, internal links, AI Overviews/featured snippets. — https://ahrefs.com/blog/seo-audit/ — **Observed practice** (vendor blog; several steps use paid Ahrefs features). Shows the industry also puts crawl/index first; differs from the course order by putting traffic drops second and links/E-E-A-T barely at all.
- What **not** to flag as audit issues (Google's own list) — "Things we believe you shouldn't focus on": "Google Search doesn't use the keywords meta tag."; "the keywords in the name of the domain (or URL path) alone have hardly any effect beyond appearing in breadcrumbs."; "The length of the content alone doesn't matter for ranking purposes (there's no magical word count target, minimum or maximum, though you probably want to have at least one word)."; "Subdomains versus subdirectories From a business point of view, do whatever makes sense for your business." — https://developers.google.com/search/docs/fundamentals/seo-starter-guide (2025-12-10) — **Documented**. **Use in L2/L3:** tool "issues" like "low word count" or "missing meta keywords" should be dropped or ranked last.
- Google on third-party audit tools: "If your SEO uses a third-party tool, keep in mind that Google doesn't evaluate or endorse third-party SEO tools, and these tools don't have access to Google's internal ranking data. Be wary of tools that claim to be "acceptable" or "approved" by Google Search." and "Before making significant changes to your site based on a third-party tool's audit, be sure to check their recommendations against official guidance from Google Search, think critically about any claims or recommendations you hear, and make your own informed decisions." and "Do they cite official Google documentation as supporting evidence for their recommendations?" — https://developers.google.com/search/docs/fundamentals/do-i-need-seo (2026-06-05) — **Documented**. **Strong anchor for "recommendations without evidence" (common failure point)** and for the course's "Evidence + Source" columns.
- Course mapping of each step to earlier modules and free tools (course synthesis, not a source):
  1. Indexing — GSC Page indexing, URL Inspection, `site:` (M06.L06, M01.L05)
  2. Crawling and status — Screaming Frog free (500 URLs), robots.txt, status codes, redirects (M06.L01–L05)
  3. Architecture and internal links — click depth, orphan pages, Content audit tab (M04.L05, M06.L05, M07.L06)
  4. On-page and content — titles, headings, intent, cannibalisation (M03.L05, M04, M07)
  5. Page experience — PSI/CrUX, HTTPS, mobile (M12)
  6. Structured data — Rich Results Test (M12)
  7. Links — GSC Links, Ahrefs Free on own site (M09)
  8. Local and international — GBP, NAP, hreflang (M11, M12)
  9. E-E-A-T and policies — spam policies, manual actions, Security issues (M14)

## 3. Prioritising: impact × effort vs Value / Chance / Effort

- Sitebulb guide (Kylee Della Volpe, published 2026-10-05): "Using the impact effort matrix is especially helpful for SEOs. The four quadrant decision making tool takes into account the amount of time and resources a fix will take and what you expect the ROI will be. You then plot that information within the appropriate quadrant to help you visualize exactly where you should be putting your efforts." and "In order to effectively use this model, you'll need to be able to estimate both your effort and your business impact." — https://sitebulb.com/resources/guides/enterprise-seo-audit-from-crawl-to-prioritised-action-plan/ — **Observed practice**.
- Same guide on template vs page fixes (useful for WordPress): "If you see the issue happening across all the pages of a certain template (like your PDPs or your blog) then you know that there's potential for this to be a template level fix. While this type of fix is a little trickier to implement because you'll need to engage your engineering team, it typically has a bigger impact because you can roll it out across all the pages in that type at once." / "If you're only seeing the issue here and there on pages within the same template, then you know this is likely a page level issue." — **Observed practice**. **Teaching point:** group 200 crawl "issues" by template (product, post, category) → a handful of fixes. That is the antidote to "an audit with 200 issues and no priorities".
- Same guide, estimating impact: "In order to estimate this we need to know three things: Current traffic to the pages where we want to place the link CTR to similar products linked on these pages types Conversion rate of PDPs of similar products Cost of the product" (list as printed; four items under "three things"). Also: "The cost of waiting - is there a cost associated with waiting?" — **Observed practice**.
- Same guide on reporting back: "Being transparent on both your wins and losses will help improve your credibility with your stakeholders for future projects." — **Observed practice**.
- Google's equivalent words: "realistic estimates of improvement, and an estimate of the work involved" (section 1) — **Documented**. Google uses neither "impact × effort" nor any scoring model.
- **Relation to the course score (course synthesis):** M10.L05 already says "Value ≈ Impact, Chance ≈ Confidence, Effort ≈ the opposite of Ease" and "keep one system". For **audit fixes** the course can keep Value / Chance / Effort with re-worded definitions: **Value** = how much the affected pages matter to the goal (traffic, revenue, bookings, template reach); **Chance** = how confident you are that the fix will help (Documented requirement broken = 3; best practice = 2; tool-only warning or "shouldn't focus on" item = 1); **Effort** = 3 for a settings change, 1 for a developer/theme job. Plus a **blocking gate** before scoring: anything that stops indexing (sitewide `noindex`, robots.txt `Disallow: /`, 5xx, manual action, hacked content) skips the queue — fix first. No source prescribes this gate; label it course rule.
- Third-party quick-win framing seen in search results (not opened): "Each finding classified in a 2×2 matrix. High impact + low effort is priority quick win. High impact + high effort is a deep project to plan by quarters." — seocom.agency — **(search-tool snippet, unverified)**. Don't quote; use only as evidence the 2×2 is common practice.

## 4. Writing a client-ready report and fix tickets

### Report (Observed practice + Google)
- Google wants recommendations explained and evidenced: "provide detailed information about your recommendations and the reasoning behind them" and "Do they cite official Google documentation as supporting evidence for their recommendations?" — https://developers.google.com/search/docs/fundamentals/do-i-need-seo — **Documented**.
- Google on expected timing (put in every report's caveats): "Every change you make will take some time to be reflected on Google's end. Some changes might take effect in a few hours, others could take several months. In general, you likely want to wait a few weeks to assess whether your work had beneficial effects in Google Search results. Keep in mind that not all changes you make to your website will result in noticeable impact in search results" — https://developers.google.com/search/docs/fundamentals/seo-starter-guide (2025-12-10) — **Documented**.
- Same idea in the drops doc: "Keep in mind that there's no guarantee that changes you make to your website will result in noticeable impact in search results. If there's more deserving content, it will continue to rank well with our systems." and "In general, you'll likely want to wait a few weeks to analyze your site in Search Console again to see if your efforts had a beneficial effect on ranking position." — https://developers.google.com/search/docs/monitor-debug/debugging-search-traffic-drops (2025-12-10) — **Documented**. Use for the "before/after evidence" rule: re-check after a few weeks, compare like-for-like periods.
- "There are no secrets here that'll automatically rank your site first in Google (sorry!)." — SEO Starter Guide — **Documented**. Good tone-setter for the report's "what we can't promise" line.
- Report structure (**Observed practice**, course synthesis; no single primary source): one-page executive summary (3–5 findings, in business language) → scope and access → baseline (dated) → findings by audit step, each with Evidence, Source + date, Value/Chance/Effort, recommendation → 90-day plan → what we checked and found fine → caveats. Common practitioner advice seen only in search summaries: "Lead with the executive summary (3-5 bullets max)" — **(search-tool snippet, unverified)**.

### Fix tickets
- Sitebulb guide (Gus Pelogia, Senior SEO Product Manager at Indeed, published 2024-11-18) gives a three-part ticket template: **Background / Work to be done / Completion criteria** (headings on the page), plus **Follow-up tasks** in its examples. — https://sitebulb.com/resources/guides/how-to-write-the-perfect-seo-ticket-for-your-devs/ — **Observed practice**. Verbatim:
  - Background: "Explain why this became an issue, what it solves and any other details about it. You can explain the impact, mention similar tickets done in the past, etc. Set the scene before the action."
  - Work to be done: "Put in detail, what you expect them to do. Structured data? Here's a template. Explain visually with images and drawings. Add the list of pages that need updating, before and after expected, etc."
  - Completion criteria: "In Scrum, this is called "Definition of Done". It's the agreed definition of complete. Does it need to be tested, and merged? Be specific like "this ticket is complete when structured data [field] is present on live pages and considered valid by this Schema/Google structured data testing tool"."
  - One task per ticket: "It's also essential to make each request one separate ticket. … Sometimes analyzing the problem is separate from the steps to solve it, similar to an audit vs implementation."
  - Reproduce: "Add examples and ways to replicate the issue. If they can't understand and replicate the issue, then there's nothing to be fixed. Show the steps, add screenshots and make it easy for them to get on the same page as you."
  - Outcomes: "Explain the impact, even if the result only comes months later. … Focusing on outcomes (results) vs outputs (finishing tasks) will help them to get more excited to work together."
  - Verification step in an example: "The SEO team will run a new crawl to verify results before the ticket is closed, keep status as "pending review"."
- Search Engine Journal, Kristina Azarenko (2021-06-02): user stories + acceptance criteria. "An SEO user story is a small recommendation that has a clear action and outcome and helps to break down big strategies into smaller steps." Example: "As an SEO manager, I want all internal links to point to the canonical URLs, so that we're sending the right signals to Google." "Acceptance criteria show how things should look when the user story is implemented correctly." "it's up to a developer how they're going to implement it since it's their area of expertise." "The best thing about Acceptance Criteria is that they can later be used for testing the implementation." — https://www.searchenginejournal.com/technical-seo-buy-in-user-stories/408878/ — **Observed practice**. Her poll claim, "most SEO professionals say that less than 40% of their SEO recommendations are implemented", is an informal social poll — **Observed practice, weak evidence**; don't present as a statistic.
  - Break big items down: "You don't want to use a huge recommendation like "I want to fix all canonicalization issues on the website." Instead, you break down the recommendation into smaller pieces." — same.
- Gray Dot Co ("How to Write SEO Engineering Tickets That Streamline Implementation"): ticket types — story (new), bug/defect ("you might submit a bug ticket if you suddenly find a number of broken redirects that were previously working"), spike ("Spikes are time-boxed and result in knowledge or proposals for future story tickets, rather than resulting in any direct code changes.") and epic. Also: "While something might feel "broken" as an SEO, it could be a new feature from a developer's perspective." — https://thegray.company/blog/writing-seo-tickets (published 2026-01-27 per page metadata; author shown as "Gray Dot Co") — **Observed practice**.
- **Teaching adaptation for small sites (course synthesis):** Nila, Kavya and Tomás have no dev team; the "ticket" is a row in a **Fix tickets** tab (or a Trello/Sheets card): ID, Finding (audit step), Evidence + source/date, Background, Work to be done, Completion criteria (testable: "URL Inspection shows 'URL is on Google'"; "Rich Results Test: 0 errors"; "old URL → 1 hop → 200"), Owner, Value/Chance/Effort, Due, Status, Before/after evidence link. Amara (agency) uses the same with a client.

## 5. Site migrations and redesigns

### 5a. Moves with URL changes (HTTP→HTTPS, domain, path changes)
All quotes from https://developers.google.com/search/docs/crawling-indexing/site-move-with-url-changes (last updated 2026-08-20) — **Documented** unless noted.
- What counts: "URL changes from HTTP to HTTPS." / "Domain name changes such as example.com to example.net or merging multiple domains or hostnames." / "URL paths changes: example.com/page.php?id=1 to example.com/widget".
- Overview steps: "Prepare the new site and test it thoroughly." / "Prepare a URL mapping from the current URLs to their corresponding new format." / "Start the site move by configuring the server to redirect from the old URLs to the new ones." / "Monitor the traffic on both the old and new URLs."
- **Change one thing at a time:** "Plan your changes to your site one after the other, not everything at the same time. For example, if you want to move your site to a new domain name, change your content management system (CMS), and update your site to use a new layout, do them one at a time: move to a new domain, then change your site's layout."
- Timing: "If your traffic is seasonal or dips on certain weekdays, it makes sense to move your site during the recurring traffic dips." (Nila: avoid Diwali gifting season.)
- **How long to settle:** "With any significant change to a site, you may experience ranking fluctuations while Google recrawls and reindexes your site. As a general rule: for medium-sized websites, it can take a few weeks or more for Google to gradually start showing the new URLs instead of the old ones (and for larger sites, even longer)." Also: "As a general rule, a small to medium-sized website can take a few weeks for most pages to move, and larger sites take longer." And: "Note that the visibility of your content in Search may fluctuate temporarily during the move. This is normal and a site's rankings will settle down over time."
- "To consider a site move complete, Googlebot will have to visit every URL on your old and new site at least once. There are no fixed crawl frequencies … The move takes place on a per-URL basis."
- Link credit: "Don't worry about link credit. 301 and other permanent redirects don't cause a loss in PageRank."
- Move all at once (small sites): "Small or medium sites: We recommend moving all URLs on your site simultaneously instead of moving one section at a time. This helps users interact with the site better in its new form, and helps our algorithms detect the site move and update our index faster." Large sites: "You can choose to move larger sites one section at a time."
- **Prepare the new site** (pre-launch checklist source): set up CMS and import; "Transfer images and downloads (such as PDF documents) that you host."; "For a move to HTTPS, get and configure the required TLS certificates on your server."; robots.txt — "some site owners block all crawling while in development. If you follow this strategy, make sure you prepare what the robots.txt file should look like once the site move starts. Likewise, if you use noindex rules during development, prepare a list of URLs from which you'll remove the noindex rules"; "if you're not moving to the new site all your old content, make sure those URLs correctly return an HTTP 404 or 410 error response code on the new site."; "verify both the old and new sites in Search Console. Be sure to verify all variants of both the old and new sites."; keep verification working ("if you're using the HTML file method … make sure you don't forget to include your current verification file in your new copy of the site"); "If you've uploaded a file to disavow links on your old site, we recommend that you re-upload it again using the Search Console account of the new site."; for a bought domain check "Manual action" and "Removed URLs … especially a site-wide URL removal."; "Ensure that your server has enough computing resources: after a migration, Google will temporarily crawl your new site more heavily than usual."
- **Old URL list** (redirect map source): "Look in your sitemaps"; "Check your server logs or analytics software for the URLs that get the most traffic"; "Check the Links to your site feature in Search Console for pages that have internal and external links"; "Use your content management system"; "Include images and videos—Make sure that you include URLs of embedded content in your site move plans: videos, images, JavaScript, and CSS files."
- Simple domain moves: "you could use a wildcard server-side redirect if you're changing your site's domain (for example, moving from example.com to example.net)."

### 5c. Domain changes and the Change of Address tool
All from https://support.google.com/webmasters/answer/9370220 (no date shown) — **Documented**.
- When: "Use the Change of Address tool when you move your website from one domain or subdomain to another: for instance, from example.com to example.org or example2.com. … Use this tool after you've moved and redirected your site."
- When not: HTTP→HTTPS (above); "Moving some pages from one location to another within your site … just add redirects, and update your sitemaps as appropriate. However, you can use the tool to migrate your site from one domain to a path within another domain."; "Moving between www and non-www in the same domain … use canonical tagging and/or redirects without using the change of address tool."; "Moving a site without any user-visible URL changes (that is, when your site URL remains the same but you are changing hosting providers or CDNs)."
- Best practices: "Don't chain site moves. If you submit a change of address to redirect traffic from site A to site B, you can't immediately submit another change of address from site B to site C."; "Try not to combine multiple moves to a single location. Moving sites A, B, and C all to new location D can cause some confusion and traffic loss."; "When moving a site, keeping the same site architecture in the new location helps to pass the signals more directly to the new site. If you combine a site move with a redesign of the site's content and URL structure in the new location, you will probably see some traffic loss as Google might need to relearn and reassess the individual pages."
- Pre-work: "Implement a 301 redirect from your old homepage to your new homepage. we recommend also implementing 301 redirects for the canonical pages on your old site." (lower-case "we" as printed)
- **Requirements:** "You must be an owner of both the old and new properties in Search Console. You must use the same Google account to manage both properties." / "The Change of Address tool can be used only on properties at the domain level … You cannot move properties at the path level, such as http://example.com/petstore/" / "The tool does not move any subdomains below the specified domain (including www). So if you specify example.com in the tool, it will not move www.example.com or m.example.com. However, all paths under the domain are affected" / "The tool moves all protocols of your source property. So if you specify http://example.com, it also moves https://example.com"
- Pre-checks: "The tool runs a few pre-move checks before telling Google about the move. If you fail any critical pre-move checks, you must fix the issue before you can continue. If you fail non-critical pre-move checks, you will see a warning with recommendations, but your request can continue." Also: "The tool runs a quick check before sending the move request to Google, to confirm that you own both sites, and to check for 301s on a few pages on your site."
- **180 days:** "If critical pre-checks pass, all sites being migrated from or to will display a notification in Search Console that the move is in progress. You will see these notifications for 180 days." / "Maintain the redirects for at least 180 days--longer if you still see any traffic to them from Google Search. Remove your old pages, but we recommend continuing to pay for the old domain for at least a year to prevent others from buying and using your abandoned domain for malicious purposes. After the 180 day period, Google does not recognize any relationship between the old and new sites, and treats the old site as an unrelated site, if still present and crawlable."
- What it does: "it tells Google to emphasize crawling and indexing your new site over crawling your old site. It also forwards various signals from the old site to the new site, and tells Google to prefer the new site over the old when determining canonical pages. These actions continue for 180 days after you start migration in Search Console."
- Old URLs can linger: "Google does not erase the old site from the index, and URLs from the old site can continue to be shown in Search results if they are available and don't have an equivalent page on the new site."
- Cancel: "You can cancel a change of address request for 180 days after it was made." Steps: remove the 301s, "Add 301 redirects from the new site to the old site.", click "Cancel Move".
- Only owners can submit it (section 1 permissions table).

### 5d. Moves without URL changes (hosting / CDN)

## Conflicts between sources

- **How long to keep redirects:** site-move doc says "generally at least 1 year" and "consider keeping redirects indefinitely"; Change of Address help says "Maintain the redirects for at least 180 days--longer if you still see any traffic". Both are Google. **Teach the longer rule** (at least a year, ideally forever, as M06.L05 already does) and explain that 180 days is the Change of Address window, after which "Google does not recognize any relationship between the old and new sites". Also keep paying for the old domain "for at least a year".
- **Old sitemap:** "At this point you can remove your old sitemap" vs "Submit the two sitemaps you saved earlier" (same doc, different sections). Practical reading: submit both during the move to watch old → new indexing, then remove the old one once it has drained.
- **Move in sections or all at once:** "Split your move into smaller steps, if that makes sense for your site" (general best practices) vs "Small or medium sites: We recommend moving all URLs on your site simultaneously" (redirect strategy). Resolution in the doc itself: sections are for **large** sites; Nila, Kavya, Tomás are small → move all at once. Mueller's split/merge comments support avoiding partial moves.
- **Crawl rate setting:** site-move doc says set "Let Googlebot determine"; the tool was deprecated in January 2024 (Google blog). Teach: nothing to set.
- **Change of Address and www:** the Help page says the tool "does not move any subdomains below the specified domain (including www)", so submit each variant; and "Don't use" it for www ↔ non-www on the same domain. Not a conflict, but easy to misread — make it a quiz item.
- **Impact × effort vs Value / Chance / Effort:** practitioner matrix has two axes and ignores confidence; the course score adds Chance. Keep one system (M10.L05) and show the matrix only as a visual of Value vs Effort.
- **Screaming Frog tutorial vs free version:** the tutorial's compare, change-detection, near-duplicate and custom-search steps are paid. Don't present them as free.

## Suggested lesson split (6 lessons, in topic order)

## Break-it lab ideas (final capstone)

**Lab A: "Nila Coffee moved from nilacoffee.in to nila.coffee last week and sales fell" (data provided).** Learners find and fix each planted error:
1. *All 140 old product URLs 301 to the new home page.* → "Don't redirect many old URLs to one irrelevant single URL destination, such as the home page … might be treated as a soft 404 error." Rebuild the redirect map one-to-one.
2. *Old URLs go `http://nilacoffee.in/x` → `https://nilacoffee.in/x` → `https://www.nila.coffee/x` → `https://nila.coffee/x/`.* → Chain of 3; "redirecting to the final destination directly".
3. *The redirects are 302s.* → Temporary: old URL stays in results. Change to 301/308.
4. *The new site's robots.txt still says `Disallow: /` from staging, and product templates carry `noindex`.* → "Don't forget to remove any noindex or robots.txt blocks that were only needed for the migration."
5. *Change of Address was submitted for `nilacoffee.in` only, not `www.nilacoffee.in`.* → "The tool does not move any subdomains below the specified domain (including www)."
6. *The intern (a Full user) "submitted" the Change of Address.* → Only owners can; check who actually did it.
7. *Canonicals on the new site still point to `nilacoffee.in`.* → "Each new URL should have a self-referencing rel="canonical"". Mueller: forgetting canonicals and nav links makes Google "keep the old URLs for much longer".
8. *The team also switched theme and rewrote all titles in the same week.* → "Change only one thing at a time"; Change of Address: "If you combine a site move with a redesign … you will probably see some traffic loss".
9. *The plan says "remove redirects after 180 days and let the old domain expire".* → Keep redirects at least a year (ideally forever) and keep paying for the old domain at least a year.
10. *GA4 tag missing from the new checkout template, so "sales fell".* → Measurement first (non-negotiable #2); compare with WooCommerce orders.
11. *Product images and the brew-guide PDF weren't moved.* → "Transfer images and downloads (such as PDF documents)".
12. *The owner panics on day 5 and wants to move back.* → "it can take a few weeks or more"; "rankings will settle down over time" (non-negotiable #14).

**Lab B: "Tomás's agency audit: 213 issues, no priorities."** A crawler export pasted into a report. Learners must: drop items Google says not to focus on ("low word count", "missing meta keywords", "keyword not in URL"); group the rest by template (e.g. 160 "missing alt text" rows = one product-template fix); spot the one blocking issue buried at row 187 (category pages `noindex`); score with Value / Chance / Effort; and rewrite the top 5 as tickets with testable completion criteria and before/after evidence.

**Lab C: "Kavya closes for a 3-week retreat."** Her developer set the whole site to 404 and used the Removals tool. Learners fix it: limited functionality (booking off, banner with `data-nosnippet`, Event schema → cancelled, opening hours updated), not 404/noindex/removals.

**Lab D (report review):** an SEO proposal sent to Amara's client promising "#1 on Google in 30 days, priority submit, approved by Google tools". Learners mark it against "Do you need an SEO?".

## Hands-on ideas (free only)

- **Scope sheet:** goal, KPI, properties (all host variants), access level per tool, date range, baseline numbers with date, out-of-scope list, deliverables, timeline. Path C: written permission + Restricted user access.
- **Audit tab:** one row per finding with columns Step (1–9) | Finding | Pages/template | Evidence | Source + date | Blocking? | Value | Chance | Effort | Total | Ticket ID. Built from GSC Page indexing, a Screaming Frog free crawl (≤500 URLs, exported to CSV), PSI, Rich Results Test, GSC Links / Ahrefs Free (own site), GBP check.
- **Template grouping exercise:** pivot the crawl CSV by template (product, post, page, category) and count issues — show how 200 rows become 8 fixes.
- **Ticket writing:** write 3 tickets (Background / Work to be done / Completion criteria) for the top findings; completion criteria must be testable with a free tool (URL Inspection, Rich Results Test, `curl -I`, Screaming Frog list mode).
- **Redirect map dry run (no live site needed):** export current URLs from the sitemap and a crawl, design a new URL scheme, map one-to-one, mark 404/410 rows, then test a sample with Screaming Frog list mode (free) or DevTools for single hops (reuse M06.L05 tab).
- **Migration checklist card:** pre-launch (crawl + save CSV, URL list from sitemap/GA4/GSC Links/CMS, map, TLS, robots/noindex plan, verify all variants, analytics on new templates, disavow re-upload if any) / launch (redirects on, remove blocks, canonicals, sitemap, Change of Address if domain) / post-launch (test redirects, crawl, Page indexing, Not found spike, update profiles and ads, annotate, check daily week 1, weekly to week 8, monthly to month 12).
- **Change of Address decision quiz:** 8 scenarios (HTTP→HTTPS, www→non-www, domain→domain, domain→path on another domain, hosting change, subdomain move, A+B+C→D, A→B→C) — use or not?
- **Pause-mode check:** `curl -I` your site with a maintenance plugin on (path A/B practice site) and record the status code; compare with Google's 503 / 200 guidance.
- **90-day plan:** three 30-day blocks of tickets, each with an "after" check date at least a few weeks after the fix; link to the Data Studio dashboard from M08 and add a Search Console annotation for every change.
- **Monthly routine calendar:** recurring reminders for the monthly report, crawl, redirect spot-check and quarterly content audit.
- **Final capstone:** full audit report (scope, baseline, findings by step with evidence, prioritised 90-day plan), fixes made with before/after screenshots or data, the Data Studio dashboard, and a short written or recorded walkthrough a site owner can follow; path C with the owner's permission. Rubric covers non-negotiables #1–#14.
