## 1. Core Web Vitals: what they are and the thresholds ⚠️ FRESHNESS

Sources:
- "Understanding Core Web Vitals and Google search results", https://developers.google.com/search/docs/appearance/core-web-vitals (last updated 2025-12-10, checked 2026-11-09)
- "Understanding page experience in Google Search results", https://developers.google.com/search/docs/appearance/page-experience (last updated 2026-09-22, checked 2026-11-09)
- web.dev "Web Vitals", https://web.dev/articles/vitals (last updated 2024-10-31); "Largest Contentful Paint (LCP)", https://web.dev/articles/lcp (2025-09-04); "Interaction to Next Paint (INP)", https://web.dev/articles/inp (2025-09-02); "Cumulative Layout Shift (CLS)", https://web.dev/articles/cls (2023-04-12); "Defining the Core Web Vitals metrics thresholds", https://web.dev/articles/defining-core-web-vitals-thresholds (2025-05-07). All checked 2026-11-09.
- PageSpeed Insights "About", https://developers.google.com/speed/docs/insights/v5/about (last updated 2024-10-21, checked 2026-11-09)

Quotes:
- "Core Web Vitals is a set of metrics that measure real-world user experience for loading performance, interactivity, and visual stability of the page. We highly recommend site owners achieve good Core Web Vitals for success with Search and to ensure a great user experience generally. This, along with other page experience aspects, aligns with what our core ranking systems seek to reward." — **Documented** (CWV page)
- "Largest Contentful Paint (LCP): Measures loading performance. To provide a good user experience, strive to have LCP occur within the first 2.5 seconds of the page starting to load." — **Documented**
- "Interaction To Next Paint (INP): Measures responsiveness. To provide a good user experience, strive to have an INP of less than 200 milliseconds." — **Documented**
- "Cumulative Layout Shift (CLS): Measures visual stability. To provide a good user experience, strive to have a CLS score of less than 0.1." — **Documented**
- ⚠️ Wording clash: Google's Search page says "less than 200 milliseconds" / "less than 0.1", while web.dev says "200 milliseconds or less" / "0.1 or less" and PSI uses closed ranges `[0, 200ms]`, `[0, 0.1]`. **Teach "200 ms or less = good"** (the PSI/web.dev definition, which is what tools apply). See Conflicts.
- Full threshold table (PSI About): "PSI sets the following thresholds in alignment with the Web Vitals initiative: | | Good | Needs Improvement | Poor | FCP | [0, 1800ms] | (1800ms, 3000ms] | over 3000ms | LCP | [0, 2500ms] | (2500ms, 4000ms] | over 4000ms | CLS | [0, 0.1] | (0.1, 0.25] | over 0.25 | INP | [0, 200ms] | (200ms, 500ms] | over 500ms | TTFB (experimental) | [0, 800ms] | (800ms, 1800ms] | over 1800ms" — **Documented**. Cheat-sheet-ready.
- 75th percentile: "a good threshold to measure is the 75th percentile of page loads, segmented across mobile and desktop devices." / "Tools that assess Core Web Vitals compliance should consider a page passing if it meets the recommended targets at the 75th percentile for all three of the Core Web Vitals metrics." — **Documented** (web.dev Web Vitals)
- Definitions:
  - LCP: "LCP reports the render time of the largest image, text block, or video visible in the viewport, relative to when the user first navigated to the page." Elements considered include "<img> elements", "An element with a background image loaded using the url() function", "Block-level elements containing text nodes". — **Documented** (web.dev LCP)
  - INP: "INP is a metric that assesses a page's overall responsiveness to user interactions by observing the latency of all click, tap, and keyboard interactions that occur throughout the lifespan of a user's visit to a page." / "The final INP value is the longest interaction observed, ignoring outliers." / "Users may also interact with the page in other ways, like hovering, zooming, or scrolling" (not counted). — **Documented** (web.dev INP)
  - CLS: "CLS is a measure of the largest burst of layout shift scores for every unexpected layout shift that occurs during the entire lifecycle of a page." / "Good CLS values are 0.1 or less." / "Poor values are greater than 0.25." — **Documented** (web.dev CLS, 2023-04-12)
- Stability: "Stable Core Web Vitals metrics won't change more than once per year." / "developers should expect the definitions and thresholds of the Core Web Vitals to be stable, and updates to have prior notice and a predictable, annual cadence." Current stages: "LCP: Stable", "CLS: Stable", "INP: Stable". No pending metric was listed on 2026-11-09. — **Documented** (web.dev Web Vitals)
- INP history: "the Chrome team decided to promote INP as the new Core Web Vitals metric for responsiveness, effective March 2024, replacing FID." — **Google public comment** (Search Central blog "Introducing INP to Core Web Vitals", Wednesday, May 10, 2023, https://developers.google.com/search/blog/2023/05/introducing-inp). "Interaction to Next Paint is now a stable Core Web Vital metric, replacing First Input Delay." — **Documented** (web.dev blog, https://web.dev/blog/inp-cwv-launch, last updated 2024-03-12). Any guide that mentions **FID** as a Core Web Vital is out of date (Myth/contested: "FID < 100 ms" still circulates).
- Ranking weight (page experience page): "Core Web Vitals are used by our ranking systems." / "getting good results in reports like Search Console's Core Web Vitals report or third-party tools doesn't guarantee that your pages will rank at the top of Google Search results" / "trying to get a perfect score just for SEO reasons may not be the best use of your time." / "Beyond Core Web Vitals, other page experience aspects don't directly help your website rank higher in search results." / "There is no single signal." / "Google Search always seeks to show the most relevant content, even if the page experience is sub-par." / "Our core ranking systems generally evaluate content on a page-specific basis … However, we do have some site-wide assessments." — **Documented**
- Self-assessment list (page experience), which maps straight onto non-negotiable #13: "Do your pages have good Core Web Vitals?", "Are your pages served in a secure fashion?", "Does your content display well on mobile devices?", "Does your content avoid using an excessive amount of ads…?", "Do your pages avoid using intrusive interstitials?", "Is your page designed so visitors can easily distinguish the main content…?" — **Documented**
- **Myth/contested:** "a Lighthouse Performance score of 90+ is a ranking factor". The Lighthouse score is a lab score. Google ranks on Core Web Vitals (field data). This is the outline's "common failure point".

## 2. Field vs lab, CrUX, PageSpeed Insights and the Search Console CWV report

Sources: web.dev "Why lab and field data can be different", https://web.dev/articles/lab-and-field-data-differences (last updated 2022-07-18); CrUX methodology, https://developer.chrome.com/docs/crux/methodology (2024-06-20); PSI About (2024-10-21); Search Console Help "Core Web Vitals report", https://support.google.com/webmasters/answer/9205520 (no date shown). All checked 2026-11-09.

- Lab vs field definitions: "Tools that report lab data—data collected in a controlled environment with predefined device and network settings." / "Tools that report field data—data collected from the real users visiting your site." / "Your lab data might indicate that your site performs great, but your field data suggests it needs improvement." / "Field data is also commonly known as Real User Monitoring (RUM) data" / "it is not just one number, it's a distribution of numbers." — **Documented** (web.dev, 2022: old but still current)
- "While all of the Core Web Vitals are, first and foremost, field metrics, many of them are also measurable in the lab." / "Tools like Lighthouse that load pages in a simulated environment without a user cannot measure INP, as there is no user input." / "the Total Blocking Time (TBT) metric is lab-measurable and is a proxy for INP." — **Documented** (web.dev Web Vitals). Key teaching point: **PSI lab never shows INP; use TBT as a clue.**
- CrUX: "The Chrome User Experience Report collects anonymized, real user measurement data for each Core Web Vital." It "powers tools like Chrome DevTools, PageSpeed Insights, and Search Console's Core Web Vitals report." — **Documented**
- CrUX eligibility: "A page must be publicly discoverable to be considered for inclusion in the CrUX dataset." / "At this time, you cannot manually submit pages or origins for inclusion." / "Experiences which meet the User and Origin criteria but not Page aren't included in the origin-level data" (sic, as published). — **Documented** (CrUX methodology)
- PSI: "PSI reports real users' … (INP), (LCP), and (CLS) experiences over the previous 28-day collection period." / "PSI will fall back to origin-level granularity" / "Sometimes the origin may also have insufficient data, in which case PSI will be unable to show any real-user experience data." / "Lab data is useful for debugging issues, as it is collected in a controlled environment." — **Documented** (already used in M10.L02)
- Search Console CWV report:
  - "The Core Web Vitals report shows how your pages perform, based on real world usage data (sometimes called field data)." — **Documented**
  - "shows URL performance grouped by status (Poor, Need improvement, Good), metric type (CLS, INP, and LCP), and URL group (groups of similar web pages)." Note the UI label is **"Need improvement"**, not "Needs improvement" (PSI's wording). — **Documented**
  - "Once a URL group has a threshold amount of data for both LCP and CLS, the URL group's status is its most poorly performing metric." / "If a URL group does not have a minimum amount of reporting data for both LCP and CLS, the URL is omitted from the report." — **Documented**
  - "Group INP: 75% of page requests took this amount of time or less with regards to responsiveness in the last 28 days." — **Documented**
  - "'No data available' … means either that your property is new in Search Console, or that there is not enough data available in the CrUX report". — **Documented**. Expect this for Nila, Kavya, Tomás and Amara (small sites): plan a **lab-only path** in the lesson.
  - Fixing: "When you think a particular issue is fixed, click Start Tracking on the issue details page". — **Documented**. The help page did not state the length of the tracking window in the extracted text. **Observed practice:** validation takes about 28 days because field data is a 28-day window. Don't quote a number as documented.

## 3. Common causes and fix briefs (LCP, INP, CLS)

Sources: web.dev "Optimize LCP", https://web.dev/articles/optimize-lcp (2025-03-31); "Optimize INP", https://web.dev/articles/optimize-inp (2025-09-02); "Optimize CLS", https://web.dev/articles/optimize-cls (2025-02-07); "Browser-level image lazy loading", https://web.dev/articles/browser-level-image-lazy-loading (2024-08-13); WordPress core dev notes (2020, 2023). All checked 2026-11-09.

**LCP**
- LCP subparts: "Time to First Byte (TTFB)", "Resource load delay", "Resource load duration", "Element render delay". Guideline split: "Time to first byte | ~40% | Resource load delay | <10% | Resource load duration | ~40% | Element render delay | <10%" / "these time breakdowns are guidelines, not strict rules." — **Documented**
- "your LCP resource should be discoverable from the HTML source." / "the LCP resource should be preloaded with a high fetch priority" (example `<link rel="preload" fetchpriority="high" as="image" …>`). — **Documented**
- "Warning: Never lazy-load your LCP image, as that will always lead to unnecessary resource load delay, and will have a negative impact on LCP." — **Documented**. Top fix-brief line for WordPress hero images.
- Compression alone may not help: compressing "would reduce the resource load duration, but it wouldn't actually improve LCP because the time would just shift to the element render delay subpart". — **Documented**. A good "think before you fix" teaching point.
- WordPress: "WordPress now automatically adds the fetchpriority attribute with a value of "high" to the image it determines most likely to be the "LCP image"" (6.3, https://make.wordpress.org/core/2023/07/13/image-performance-enhancements-in-wordpress-6-3/). "By default, WordPress will add loading="lazy" to all img tags that have width and height attributes present." (5.5, https://make.wordpress.org/core/2020/07/14/lazy-loading-images-in-5-5/). — **Documented** (WordPress core). ⚠️ Themes, sliders and page builders can override this, which is **Observed practice**. Check the hero `<img>` in View Source.

**INP**
- An interaction has three parts: "The input delay … The processing duration … The presentation delay". "An input delay occurs until event handlers start running, possibly caused by factors such as long tasks on the main thread." / "Yield to the main thread often". — **Documented**
- **Observed practice** (fix-brief language for non-developers): heavy third-party scripts (chat widgets, tag managers, sliders), page-builder JS. web.dev lists "Script evaluation and long tasks" and "Avoid large, complex layouts and layout thrashing" as headings. Teach the learner to **write a brief for a developer**, not to rewrite JS.

**CLS**
- "The most common causes of a poor CLS are:" "Images without dimensions." "Ads, embeds, and iframes without dimensions." "Dynamically injected content such as ads, embeds, and iframes without dimensions." "Web fonts." — **Documented** (Optimize CLS)
- "we recommend adding width and height attributes to all <img> tags" / "Without width and height specified, image dimensions default to 0×0 pixels." — **Documented** (web.dev lazy loading)
- "CLS often happens while the user scrolls through a page, when lazy-loaded content loads fully without space reserved for it." — **Documented**

**Fix brief template idea (Observed practice; not a Google format):** Template | URL group example | Metric failing (field, p75) | Lab clue (PSI diagnostic) | Likely cause (cite web.dev cause) | Proposed fix | Owner | How we'll verify (PSI lab now, CWV report "Start Tracking", recheck after 28 days).

## 4. Mobile-first indexing and HTTPS

Sources: "Mobile site and mobile-first indexing best practices", https://developers.google.com/search/docs/crawling-indexing/mobile/mobile-sites-mobile-first-indexing (last updated 2025-12-10); blog "Mobile-first indexing has landed", https://developers.google.com/search/blog/2023/10/mobile-first-is-here (Tuesday, October 31, 2023); Search Console Help "HTTPS report", https://support.google.com/webmasters/answer/11396518 (no date shown); blogs "HTTPS as a ranking signal" (Thursday, August 07, 2014) https://developers.google.com/search/blog/2014/08/https-as-ranking-signal and "Indexing HTTPS pages by default" (Thursday, December 17, 2015) https://developers.google.com/search/blog/2015/12/indexing-https-pages-by-default; web.dev "What is mixed content?", https://web.dev/articles/what-is-mixed-content (2019-09-07); MDN "Strict-Transport-Security", https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Strict-Transport-Security (no date in extracted text). All checked 2026-11-09.

**Mobile-first**
- "Google uses the mobile version of a site's content, crawled with the smartphone agent, for indexing and ranking." — **Documented**
- "Google recommends Responsive Web Design because it's the easiest design pattern to implement and maintain." — **Documented**
- "Make sure that content is the same on desktop and mobile" / "You can have a different design on mobile to maximize user experience (for example, moving content into accordions or tabs); just make sure that the content is equivalent to the desktop site, since indexing on your site comes from the mobile site." — **Documented**
- "Use the same clear and meaningful headings on the mobile site" / "Make sure that the title element and the meta description are equivalent across both versions" / "Use the same robots meta tags on the mobile and desktop site." / "Don't lazy-load primary content upon user interaction." — **Documented**
- 2023 post: "a mobile web page now needed to be as complete as the corresponding desktop version." Remaining desktop-crawled sites have issues such as "the mobile version of the site is blocked with robots.txt while the desktop version is allowed". — **Google public comment** (blog, 2023-10-31)
- Tools: Google "Removed mentions of the Mobile Friendly Test and the Mobile Usability report throughout" (updates log, December 1, 2023). — **Documented**. Don't send learners to the Mobile-Friendly Test. Use URL Inspection (Crawled as / screenshot in live test), the Rich Results Test (smartphone default) or Lighthouse.

**HTTPS**
- Page experience: "Are your pages served in a secure fashion?" — **Documented**
- HTTPS report: "The HTTPS report shows how many indexed URLs on your site are HTTP vs HTTPS." / "Ideally your site should have no HTTP URLs in the report". Reasons include "HTTP marked with canonical tag" ("you should declare the HTTPS as the canonical page") and "HTTPS has invalid certificate". — **Documented**
- History: HTTPS is "a very lightweight signal—affecting fewer than 1% of global queries, and carrying less weight than other signals such as high-quality content" (2014). "our systems prefer the HTTPS version by default, you can also make this clearer for other search engines by redirecting your HTTP site to your HTTPS version and by implementing the HSTS header on your server." (2015) — **Google public comment** (blog posts; old, so label the dates)
- Mixed content: "Most browsers now block mixed content for security reasons." "There are two types of mixed content: active and passive." "Passive mixed content, including images, video, and audio" / "Attacks on active mixed content let an attacker do almost anything to the page." — **Documented** (web.dev, 2019: old, flag)
- HSTS concept: "The HTTP Strict-Transport-Security response header (often abbreviated as HSTS) informs browsers that the host should only be accessed using HTTPS, and that any future attempts to access it using HTTP should automatically be upgraded to HTTPS." / "When using preload, the max-age directive must be at least 31536000 (1 year), and the includeSubDomains directive must be present." / "To disable HSTS, set max-age=0." — **Documented** (MDN). **Teach as a concept only:** HSTS (and especially preload) is hard to undo. Learners on shared hosting should ask their host, not edit headers blind (Observed practice).
- Site moves: the site-move guide lists "URL changes from HTTP to HTTPS" as a site move and says "Search Console is your friend, especially during a site move." https://developers.google.com/search/docs/crawling-indexing/site-move-with-url-changes (last updated 2026-08-20). — **Documented**. Redirect rules already taught in M06.L05.

## 5. JavaScript SEO

Sources: "Understand JavaScript SEO basics", https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics (last updated 2026-03-04); "Fix Search-related JavaScript problems", …/javascript/fix-search-javascript (2025-12-18); "Fix lazy-loaded content", …/javascript/lazy-loading (2025-12-10); "Dynamic rendering as a workaround", …/javascript/dynamic-rendering (2025-12-10); "Make your links crawlable", https://developers.google.com/search/docs/crawling-indexing/links-crawlable (2025-12-10); Search Console Help "URL Inspection tool", https://support.google.com/webmasters/answer/9012289 (no date shown); "Generate structured data with JavaScript", …/structured-data/generate-structured-data-with-javascript (2025-12-10); web.dev "Rendering on the Web", https://web.dev/articles/rendering-on-the-web (2026-01-05). All checked 2026-11-09.

- Pipeline: "Googlebot queues all pages with a 200 HTTP status code for rendering, unless a robots meta tag or header tells Google not to index the page. The page may stay on this queue for a few seconds, but it can take longer than that. Once Google's resources allow, a headless Chromium renders the page and executes the JavaScript. Googlebot parses the rendered HTML for links again … Google also uses the rendered HTML to index the page." — **Documented**
- "If the HTTP status code is non-200 (for example, on error pages with 404 status code), rendering might be skipped." / "server-side or pre-rendering is still a great idea because it makes your website faster for users and crawlers, and not all bots can run JavaScript." — **Documented**
- noindex trap: "When Google encounters the noindex tag, it may skip rendering and JavaScript execution, which means using JavaScript to change or remove the robots meta tag from noindex may not work as expected. If you do want the page indexed, don't use a noindex tag in the original page code." — **Documented** (links to non-negotiable #7)
- Canonical via JS: "The best way to set the canonical URL is to use HTML" / "make sure that this is the only rel="canonical" link tag on the page." — **Documented**
- SPAs: "use the History API" / "don't use fragments to load different page content." / "The AJAX-crawling scheme has been deprecated since 2015, so you can't rely on URL fragments to work with Googlebot." / "Expect Googlebot to decline user permission requests." — **Documented**
- Caching: "Googlebot caches aggressively … WRS may ignore caching headers. This may lead WRS to use outdated JavaScript or CSS resources." — **Documented**
- **Links:** "Generally, Google can only crawl your link if it's an <a> HTML element (also known as anchor element) with an href attribute." Parseable: `<a href="/products/category/shoes" onclick="javascript:goTo('shoes')">`. "Not recommended (but Google may still attempt to parse this): <a routerLink="products/category"> <span href="https://example.com"> <a onclick="goto('https://example.com')">" and `<a href="javascript:goTo('products')">`. "Links are also crawlable when you use JavaScript to insert them into a page dynamically as long as it uses the HTML markup shown above." / "If you are using JavaScript to insert anchor text, use the URL Inspection Tool to make sure it's present in the rendered HTML." — **Documented**. Break-it lab material.
- **Lazy loading:** "make sure that your lazy-loading implementation loads all relevant content whenever it is visible in the viewport." Methods ("Browser built-in lazy-loading", "IntersectionObserver API") "don't rely on user actions, such as scrolling or clicking, to load content, which is important as Google Search does not interact with your page." Infinite scroll: "support paginated loading" and "update the displayed URL using the History API". — **Documented**
- **Testing tools:** "To test how Google crawls and renders a URL, use the Rich Results Test or the URL Inspection Tool in Search Console. You can see loaded resources, JavaScript console output and exceptions, rendered DOM, and more information." — **Documented**
- URL Inspection: "To see additional response data such as the raw HTML returned, the HTTP headers, JavaScript console output, and any page resources loaded, click View crawled page." / "A screenshot of the rendered page is available only in a live test." / "View a rendered version of the page: See a screenshot of how the Google-InspectionTool sees the page." / "click View crawled page > More info (indexed result) or View tested page > More info (live test)." / "You can determine the canonical version only in the indexed data; the live test cannot predict whether or not the tested version will be considered canonical." — **Documented**. ⚠️ See Conflicts: the Help wording "raw HTML returned" vs practitioners' view that the HTML tab shows the rendered DOM.
- **Free method without Search Console (Path B):** Rich Results Test → "View tested page" → HTML / Screenshot. Compare with View Source (Ctrl+U) for a phrase. This is the "source vs rendered" check. — **Documented** (both tools named by Google for render checks)
- **Dynamic rendering status:** "Dynamic rendering was a workaround and not a long-term solution for problems with JavaScript-generated content in search engines. Instead, we recommend that you use server-side rendering, static rendering, or hydration as a solution." / "Dynamic rendering is a workaround and not a recommended solution, because it creates additional complexities and resource requirements." / "Googlebot generally doesn't consider dynamic rendering as cloaking." — **Documented** (still published as a workaround, not removed. Teach "deprecated as advice; avoid for new builds").
- Rendering vocabulary (web.dev): "Server-side rendering (SSR) Rendering an app on the server to send HTML, rather than JavaScript, to the client." / "Client-side rendering (CSR) Rendering an app in a browser, using JavaScript to modify the DOM." / "we encourage developers to consider server-side rendering or static rendering over a full rehydration approach." — **Documented**

## 8. M12 schema types: key requirements

All from Google Search Central structured-data docs, checked 2026-11-09. All **Documented**.

- **Product, two experiences** (https://developers.google.com/search/docs/appearance/structured-data/product, 2025-12-10): "Product snippets: For product pages where people can't directly purchase the product." / "Merchant listings: For pages where customers can purchase products from you." / "adding the required product information properties for merchant listings means that your product pages can also be eligible for product snippets." / "Providing both structured data on web pages and a Merchant Center feed maximizes your eligibility". Nila's shop = merchant listing. Nila's brew-guide "best grinders" review post = product snippet.
- **Merchant listing** (…/merchant-listing, 2026-09-08): eligible displays include "the shopping knowledge panel, Google Images, popular product results, and product snippets". "Only pages where a shopper can purchase a product are eligible for merchant listing experiences, not pages with links to other sites that sell the product." Required on Product: `name`, `image`, `offers`. For offers: "merchant listings require an Offer as the merchant has to be the seller". Offer required: "price or priceSpecification.price" and "priceCurrency" ("three-letter ISO 4217 format", so `INR` for Nila). "Unlike product snippets, merchant listing experiences require a price greater than zero." May 2026 addition: `hasAdultConsideration` (updates log, May 20, 2026).
- **Product snippet** (…/product-snippet, 2026-09-08): required `name` plus "You must include one of the following properties: review, aggregateRating, offers" (as listed in the type table). "Only editorial product review pages are eligible for the pros and cons appearance in Search, not merchant product pages or customer product reviews."
- **Review snippet** (…/review-snippet, 2026-09-08): "Make sure the review content you mark up are readily available to users from the marked-up page." / "If you use AggregateRating, users should be able to see that aggregate rating on the page." / "Don't aggregate reviews or ratings from other websites." Self-serving rule: "If the entity that's being reviewed controls the reviews about itself, their pages that use LocalBusiness or any other type of Organization structured data are ineligible for star review feature. For example, a review about entity A is placed on the website of entity A, either directly in their structured data or through an embedded third-party widget (for example, Google Business reviews or Facebook reviews widget)". ⚠️ Big point for **Kavya** (yoga studio) and **Tomás** (shop LocalBusiness): stars on their own LocalBusiness pages are not eligible. Product reviews on Nila's product pages are a different case (Product type).
- **Organization** (…/organization, 2026-09-08): "There are no required properties". "We recommend placing this information on your home page, or a single page that describes your organization, for example the about us page." Some properties "are used behind the scenes to disambiguate your organization (like iso6523 and naics)", others "can influence visual elements … (such as which logo is shown …)". Merchants can influence the "merchant knowledge panel and brand profile, such as return policy, address, and contact information." Ties to M11 non-negotiable #12 (one identity).
- **Article** (…/article, 2026-09-08): types "Article, NewsArticle, BlogPosting"; "There are no required properties"; can help Google "show better title text, images, and date information". "there's no markup requirement to be eligible for Google News features like Top stories".
- **BreadcrumbList** (…/breadcrumb, 2026-09-08): "define a BreadcrumbList that contains at least two ListItems." / "We recommend providing breadcrumbs that represent a typical user path to a page, instead of mirroring the URL structure." / "It is not required to include a breadcrumb ListItem for the top level path … nor for the page itself." Desktop-only display since January 2025 (section 6).
- **LocalBusiness** (…/local-business, 2026-09-08): can feed "a prominent Google knowledge panel with details about a business". Opening-hours patterns are documented ("To show a business as open 24 hours a day, set the open property to "00:00" and the closes property to "23:59""; seasonal hours with `validFrom`/`validThrough`). M11 introduced it; M12 validates it.
- **VideoObject** (…/video, last updated 2026-09-24): "you can influence the information that's shown in video results, such as the description, thumbnail URL, upload date, and duration". Key moments: "Clip structured data" or "SeekToAction structured data"; "To opt out of the key moments feature completely …, use the nosnippet meta tag." URL Inspection video issue: "You should provide the same title, thumbnail URL, and video URL in all sources (sitemap, HTML tags, meta tags, and structured data)". Kavya's class videos are a natural example.

## 9. Rich Results Test vs Schema Markup Validator

Sources: Search Console Help "Rich Results Test", https://support.google.com/webmasters/answer/7445569 (no date shown); blog "An update on the Structured Data Testing Tool", https://developers.google.com/search/blog/2020/12/structured-data-testing-tool-update (Tuesday, December 15, 2020). Checked 2026-11-09.

- RRT: "The test shows which rich result types were found on the page, as well as any errors or suggestions for your structured data." / "The default user agent is smartphone". It reports "Crawled successfully / Crawl failed" and "Crawled as", and checks robots.txt blocking of the page and resources ("a blocked large image could make a page appear to be mobile-friendly when it is not"). — **Documented**
- Schema Markup Validator (validator.schema.org): "The main purpose of the tool will be to check syntax and compliance of markup with schema.org standards. To test your markup for Google Search rich result types, you can continue to use the Rich Results Test." / "the Rich Results Test and Search Console are the best tools to make sure your markup is valid for Google Search." — **Google public comment** (2020 blog)
- Teaching rule (**Observed practice** built on the above): **SMV = "is this valid schema.org?"** (any type, any engine). **RRT = "is this eligible for a Google rich result?"** (Google features only; deprecated types like FAQ/HowTo no longer appear). A page can pass SMV and show "No items detected" for rich results in RRT. Both are free, with no login.
- validator.schema.org returned a JS-only shell to curl (no readable text). The schema.org blog announcement returned HTTP 429. See Not found.

## 10. International SEO: URL structures, hreflang, x-default, no locale redirects

Sources: "Managing multi-regional and multilingual sites", https://developers.google.com/search/docs/specialty/international/managing-multi-regional-sites (2025-12-10); "Tell Google about localized versions of your page", …/international/localized-versions (last updated 2026-09-21); "How Google crawls locale-adaptive pages", …/international/locale-adaptive-pages (2025-12-10); blog "Introducing "x-default hreflang" for international landing pages" (Wednesday, April 10, 2013). All checked 2026-11-09.

- URL structure table (verbatim pros/cons): ccTLD `example.de` — Pros "Clear geotargeting", "Server location irrelevant", "Easy separation of sites"; Cons "Expensive (can have limited availability)", "Requires more infrastructure", "Strict ccTLD requirements (sometimes)", "Can only target a single country". Subdomain `de.example.com` — Pros "Easy to set up", "Allows different server locations", "Easy separation of sites"; Cons "Users might not recognize geotargeting from the URL alone (is "de" the language or country?)". Subdirectory `example.com/de/` — Pros "Easy to set up", "Low maintenance (same host)"; Cons "Users might not recognize geotargeting from the URL alone", "Single server location", "Separation of sites harder". URL parameters `site.com?loc=de` — "Not recommended." — **Documented**
- Signals: ccTLDs "provide a strong signal"; "We also treat some vanity ccTLDs (such as .tv and .me) as gTLDs". Server location "is not a definitive signal". Other signals: "local addresses and phone numbers on the pages, the use of local language and currency, links from other local sites, or signals from your Business Profile". "Google ignores locational meta tags (like geo.position or distribution) or geotargeting HTML attributes." — **Documented**
- Language detection: "Google uses the visible content of your page to determine its language. We don't use any code-level language information such as lang attributes, or the URL." Also: "Google doesn't use hreflang or the HTML lang attribute to detect the language of a page; instead, we use algorithms". — **Documented**
- **No auto-redirects:** "Avoid automatically redirecting users from one language version of a site to a different language version of a site. For example, don't redirect based on what you think the user's language may be." / "Consider adding hyperlinks to other language versions of a page." — **Documented**
- **Locale-adaptive (IP/Accept-Language) pages:** "the default IP addresses of the Googlebot crawler appear to be based in the USA. In addition, the crawler sends HTTP requests without setting Accept-Language in the request header." / "Important: We recommend using separate locale URL configurations and annotating them with rel="alternate" hreflang annotations." — **Documented**
- **hreflang rules:**
  - Three methods (HTML tags, HTTP headers, sitemap): "The three methods are equivalent from Google's perspective". "there's no benefit in Search" in using all three. — **Documented**
  - **Self-reference:** "Each language version must list itself as well as all other language versions." — **Documented**
  - **Return links:** "If two pages don't both point to each other, the tags will be ignored." — **Documented**
  - "Alternate URLs must be fully-qualified, including the transport method (http/https)". "Alternate URLs do not need to be in the same domain." "The <link> tags must be inside a well-formed <head> section of the HTML." — **Documented**
  - Codes: "language code (in ISO 639-1 format) followed by an optional second code that represents the region code (in ISO 3166-1 Alpha 2 format)". "other codes that aren't listed in those standards, such as es-419, aren't supported." "The hreflang value is case-insensitive". — **Documented**. Classic error to plant: `en-UK` (UK isn't the ISO 3166-1 code; it's GB). **Observed practice**: the doc page didn't spell out the en-UK example in extracted text.
  - **x-default:** "The reserved x-default value is used when no other language/region matches the user's browser setting." / "it was designed for language selector pages". 2013 blog: "signals to our algorithms that this page doesn't target any specific language or locale and is the default page when no other page is better suited." — **Documented / Google public comment**
  - Duplicates: "Localized versions of a page are only considered duplicates if the main content of the page remains untranslated." Same-language regional duplicates: "pick a preferred version and use the rel="canonical" element and hreflang tags". — **Documented**
  - June 2025: "Removed a section from our multilingual documentation about using robots.txt to block all automatically translated pages." (updates log). — **Documented**
- Running example fit: Nila (India) may add `en-IN` + a Tamil (`ta`) brew guide, or sell to `en-AE`/`en-GB`. Amara's agency could plan `/en/` + `/es/` subfolders. Tomás is a Spanish/English example candidate. (Course design, not a source claim.)
- Other engines (outline "one note"): official Bing, Yandex, Naver, Baidu or Seznam hreflang pages were **not found** (see Not found).

## Break-it lab ideas

**Planted files: "Nila Coffee staging" (a product page, a brew-guide post, a hreflang set). Learners find and fix each error.**

1. **Failing Product markup (merchant listing):** `"price": "0"`, `"priceCurrency": "Rs"`, no `image`, `offers` as `AggregateOffer` on Nila's own shop page, and an `aggregateRating` of 4.9 from 212 reviews that appear nowhere on the page. → Fix: price > 0 ("merchant listing experiences require a price greater than zero"), `INR` ("three-letter ISO 4217 format"), add `image`, use `Offer` ("merchant listings require an Offer"), and remove or show the rating ("users should be able to see that aggregate rating on the page"). Check in RRT (merchant listing + product snippet sections) and SMV (syntax only).
2. **Markup for content not on the page:** `FAQPage` JSON-LD with 6 Q&As that aren't visible, added by an "AI SEO" plugin "for AI Overviews". → Two errors: invisible content ("Don't mark up content that is not visible") and an obsolete feature (FAQ ended 7 May 2026). Plus Google: "Structured data isn't required for generative AI search".
3. **Self-serving stars:** Kavya's studio home page has LocalBusiness + AggregateRating pulled from a Google reviews widget. → Ineligible: "a review … through an embedded third-party widget (for example, Google Business reviews …)". Remove the rating markup; keep the reviews visible for people.
4. **JS-only link:** the brew-guide "Next: French press guide" button is `<span onclick="location.href='/french-press'">` and the category menu is `<a routerLink="…">`. → Not crawlable. Fix with `<a href="/brew-guides/french-press/">French press guide</a>`. Verify with View Source and the rendered HTML (live test / RRT).
5. **Lazy-load on scroll only:** recipe steps 4–9 load only after a "Load more" click. → "Google Search does not interact with your page". Load in the viewport or server-render.
6. **noindex in source, removed by JS:** `<meta name="robots" content="noindex">` in the template and a script that removes it after load. → "it may skip rendering" — page stays out of the index (#7).
7. **Lazy-loaded hero (LCP) image without dimensions:** `<img loading="lazy" src="hero.jpg">` at the top of the home page. → "Never lazy-load your LCP image". Add `width`/`height` (CLS) and `fetchpriority="high"`.
8. **Broken hreflang set** (Nila: `/en-in/`, `/ta-in/`, `/en-gb/`):
   - `/en-in/` lists `/ta-in/` and `/en-gb/` but not itself → "must list itself".
   - `/en-gb/` has no tags pointing back → "If two pages don't both point to each other, the tags will be ignored."
   - `hreflang="en-UK"` → invalid region (ISO 3166-1 is GB).
   - `href="/ta-in/"` (relative) → "must be fully-qualified".
   - `x-default` points to `/en-in/` while the site also IP-redirects UK visitors to `/en-gb/` → no auto-redirects ("don't redirect based on what you think the user's language may be"). Googlebot "appear[s] to be based in the USA". Use a selector page as x-default.
   - `/ta-in/` canonical points to `/en-in/` → canonical must not point across languages ("only considered duplicates if the main content … remains untranslated").
9. **Mixed content:** HTTPS product page loads `http://cdn…/beans.jpg` and an `http://` script. → Passive vs active; the browser blocks it. Fix the URLs to HTTPS.
10. **Faceted trap (Tomás):** `?size=&material=&brand=` in any order, empty combos return 200 "No products found", and a `noindex` used to "save crawl budget". → Consistent order, 404 for empty combos, robots.txt disallow for non-indexable facets; "Don't use noindex" for crawl budget.

## Hands-on ideas (free only)

- **CWV for 3 templates (capstone part 1):** PSI on Nila's home, one product and one brew-guide post. Record field (p75 LCP/INP/CLS, or "no data") and lab (LCP, CLS, TBT). Then the Search Console CWV report (Path A) or "No data available" (expected). Write one fix brief per template using the template in section 3.
- **Hero image check:** View Source on the home page: is the first big `<img>` `loading="lazy"`? Does it have `fetchpriority="high"`, `width` and `height`? Note theme or page-builder overrides (links to M05.L04).
- **Mobile parity check:** compare desktop and phone (DevTools device mode, no Lighthouse run needed) for main content, headings, title and meta. URL Inspection **Crawled as** (Path A).
- **HTTPS sweep:** padlock and DevTools Console "Mixed Content" warnings on 5 pages. Search Console HTTPS report (Path A). Check `http://` → `https://` is a single 301 (M06.L05). Note whether an HSTS header is present (DevTools Network → Headers). Don't add one blind.
- **JS rendering check (capstone part 2):** pick a phrase and a link from a JS-heavy element (slider, tabs, "related posts" widget). Is it in View Source? In URL Inspection live test HTML + screenshot (Path A), or RRT "View tested page" HTML (Path B)? Record "source / rendered / both / missing".
- **Structured data on 2 pages (capstone part 3):** Nila product page (merchant listing: name, image, offers with price + INR, availability; reviews only if visible) and a brew-guide post (Article/BlogPosting + BreadcrumbList). Validate in RRT and SMV, record both results, and fix until RRT shows "valid items" with no critical issues. Kavya variant: LocalBusiness (no self-serving stars) + VideoObject for a class video. Tomás variant: Product snippet vs merchant listing decision.
- **Retired-features audit:** run RRT on 3 competitor or own pages. List any FAQPage/HowTo/ClaimReview markup found and mark "no Google rich result since <date>".
- **International plan (capstone part 4, if relevant):** choose subfolder vs subdomain vs ccTLD for Nila (India + Tamil + UK) using Google's pros/cons table. Write a full hreflang set (self, return links, x-default selector page). If not relevant (Kavya), write a short "why we don't need hreflang" note.
- **Facet map (Tomás):** list filter parameters from his category URLs. Decide "index" (e.g. one brand page with demand) vs "block" for each. Draft robots.txt `disallow` lines and test them in Search Console's robots.txt report (M06.L02) or Bing's robots.txt tester.
- **Go further: logs.** If the host gives raw access logs, filter one day for "Googlebot", verify 2 IPs with `host` (reverse then forward) and count status codes. Otherwise read the Crawl Stats report (Path A, root-level property only).
- **Capstone wrap:** advanced technical report = CWV table + 3 fix briefs, JS rendering result, 2 validated schema pages (screenshot prompts, not renders), hreflang/international plan or the "not needed" note, plus a #13 checklist (HTTPS ✓, mobile parity ✓, CWV good or fix plan ✓, markup matches visible content ✓).
