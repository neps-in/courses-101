## 4. Permalinks and URL changes

**Settings → Permalinks labels (from 7.1 source `wp-admin/options-permalink.php`, not tested live):** "Permalink Settings", "Common Settings", "Plain", "Day and name", "Month and name", "Numeric", "Post name", "Custom Structure", "Available tags:", "Optional", "Category base", "Tag base", and the notice "Permalink structure updated."

- **Documented, WordPress screen text (7.1 source):** "Select the permalink structure for your website. Including the %s tag makes links easy to understand, and can help your posts rank higher in search engines." (`%s` is `%postname%`.) **Myth/contested** as a ranking claim; see Google below and Conflicts.
- **Documented, Google:** "From a ranking perspective, the keywords in the name of the domain (or URL path) alone have hardly any effect beyond appearing in breadcrumbs." SEO Starter Guide, last updated 2025-12-10. https://developers.google.com/search/docs/fundamentals/seo-starter-guide
- **Documented, Google:** "When possible, use readable words rather than long ID numbers in your URLs." and "we recommend using hyphens (-) instead of underscores (_) to separate words in your URLs". URL structure best practices, last updated 2026-10-21. https://developers.google.com/search/docs/crawling-indexing/url-structure
- **Documented, WordPress docs:** "Permalinks are the permanent URLs of your posts, pages, categories, and other archive pages on your website. These URLs are permanent and should never be changed — hence the name permalink." and "The default values for Category base and Tag base are category and tag. You can change them, but you can't remove them from the URLs altogether." https://wordpress.org/documentation/article/customize-permalinks/ (modified 2025-06-28)
- **Documented, WordPress docs:** "By default, WordPress uses web URLs that have day and name in them". https://wordpress.org/documentation/article/settings-permalinks-screen/ (last updated June 8, 2024, so it is **older than 7.x**; its labels still match the 7.1 source.)
- **Documented, WordPress 7.1 source, old-slug redirect (`_wp_old_slug`):**
  - `wp_check_for_changed_slugs()` in `wp-includes/post.php` has the comment "We're only concerned with published, non-hierarchical objects." It runs `add_post_meta( $post_id, '_wp_old_slug', $post_before->post_name )`.
  - `wp_old_slug_redirect()` in `wp-includes/query.php` (`@since 2.1.0`) runs only when `is_404()`, with the comment "Do not attempt redirect for hierarchical post types." It ends with `wp_redirect( $link, 301 ); // Permanent redirect.`
  - **What this means:** a changed slug on a **published post** gets a 301. **Pages** (hierarchical) don't. A slug changed while the post is still a draft isn't stored. This matches WordPress 101 M05.L02 (2026-10-31).
- **Documented, WordPress 7.1 source, changing the structure:** `redirect_guess_404_permalink()` in `wp-includes/canonical.php` (`@since 2.3.0`) "Attempts to guess the correct URL for a 404 request based on query vars." It only runs `if ( get_query_var( 'name' ) )`. It matches `post_name LIKE` the requested name (a loose prefix match by default; `strict_redirect_guess_404_permalink` "Default false (loose guess)"). It can be switched off with `do_redirect_guess_404_permalink`. **So after a structure change, the old URL is only rescued if WordPress can read a post name out of it, and the loose match can land on the wrong post.** That is an inference from the code, **not tested live**. Teach "plan redirects and test every top URL", as WordPress 101 M01.L04 does.
- **Documented, Google redirects:** "Permanent redirects: Show the new redirect target in search results." and "Use permanent redirects when you're sure that the redirect won't be reverted." Redirects and Google Search, last updated 2026-04-14. https://developers.google.com/search/docs/crawling-indexing/301-redirects
- **Documented, Google site moves** (last updated 2026-08-20; its scope includes "URL paths changes: example.com/page.php?id=1 to example.com/widget"):
  - "Prepare a URL mapping from the current URLs to their corresponding new format."
  - "Expect temporary fluctuation in site ranking during the move."
  - "As a general rule: for medium-sized websites, it can take a few weeks or more for Google to gradually start showing the new URLs instead of the old ones (and for larger sites, even longer)."
  - "Keep the redirects for as long as possible, generally at least 1 year."
  - "Change the internal links on the new site from the old URLs to the new URLs."
  - https://developers.google.com/search/docs/crawling-indexing/site-move-with-url-changes

## 5. Categories, tags and archive pages

- **Documented, Google:** "Some duplicate content on a site is normal and it's not a violation of Google's spam policies." Canonicalization, last updated 2026-08-20. https://developers.google.com/search/docs/crawling-indexing/canonicalization
- **Documented, Google:** "Scaled content abuse is when many pages are generated for the primary purpose of manipulating search rankings and not helping users." Spam policies, last updated 2026-08-28. https://developers.google.com/search/docs/essentials/spam-policies. **Don't** imply that tag archives count as scaled content abuse; no Google page found says so.
- **Google public comment** (John Mueller, Google+ Webmaster Hangout, reported 2015-04-27 by Search Engine Roundtable): "I think there are some kind of tag pages that are essentially going to search results pages, which probably don't make sense to get indexed. There are other kinds of tag pages that are almost like category pages where you have a useful collection of individual pieces of content that match this category. And that might be something you do want to have indexed." and "So that's not something where I'd say there is a default answer that works well for everyone." https://www.seroundtable.com/google-tag-pages-index-20211.html. **Freshness flag:** 11 years old, secondhand transcript.
- **Documented, WordPress 7.1 source, core `noindex` behaviour.** `wp-includes/default-filters.php` adds only these `wp_robots` filters on the front end: `wp_robots_noindex` (only when `! get_option( 'blog_public' )`, i.e. search engine visibility off), `wp_robots_noindex_embeds`, `wp_robots_noindex_search` (`if ( is_search() )`), and `wp_robots_max_image_preview_large`. **Core adds no `noindex` to category, tag, author or date archives.**
- **Documented, WordPress 7.1 source, core sitemap.** `class-wp-sitemaps-taxonomies.php` "Returns all public, registered taxonomies" and queries with `'hide_empty' => true`. So category and tag archives that have posts are listed in `wp-sitemap.xml` by default.
- **Observed on blog.12026.store** (WordPress 7.1 per its `generator` tag, read-only, 2026-11-08): the category archive `/category/uncategorized/` had `<meta name='robots' content='max-image-preview:large' />` (no `noindex`). A search URL `/?s=test` had `noindex, follow, max-image-preview:large`. Its `wp-sitemap.xml` lists `wp-sitemap-taxonomies-category-1.xml` and no tag sitemap. That fits `hide_empty`, assuming the site has no tags in use. This confirms the core behaviour above on a live site.
- **Observed practice:** SEO plugins offer to `noindex` tag, date and author archives, and many site owners `noindex` thin tag archives. WordPress 101 M05.L02 already covers author and date archives in Yoast; tags are a judgement call (see Mueller). **Myth/contested:** "tag pages cause a duplicate-content penalty". Google's canonicalization page above says some duplication is normal, and no penalty doc was found.
- **Course framing (suggested):** the failure point "tag pages that duplicate posts" comes down to quality and usefulness, not a penalty. Tags used once make archive pages listing one post that only repeat that post's excerpt. Fix it with the WordPress 101 tag rule, then decide per tag whether to `noindex` it.

## 8. Page builders vs the block editor

- **Documented, HTTP Archive Web Almanac 2025, CMS chapter** (published 2026-01-15; authors Arabian, Knauss, Güler, Kochba, Fatola, Bhattacharya). https://almanac.httparchive.org/en/2025/cms

  - "Builders that reduce markup overhead, avoid global asset loading, and integrate deeply with the Block Editor tend to limit performance costs more effectively."
  - "WordPress remains among the lowest-ranked with a pass rate of 45%." (share of sites passing all three Core Web Vitals)
  - **Not found:** a per-builder Core Web Vitals comparison (for example Elementor pages vs block-editor pages). The chapter's builder-performance statements are qualitative. **Don't say "the Almanac proves page builders are X% slower."**
- **Documented, Web Almanac 2024, CMS chapter** (2024-11-11): "Elementor is used on 54% of desktop sites and 56% on mobile, wpBakery is 21% and 21% for both, Divi 14% for both" and "Historically, page builders have been anecdotal indicators of poor performance." https://almanac.httparchive.org/en/2024/cms

This was about bloat in general, **not page builders by name**. https://www.seroundtable.com/google-seo-bloated-sites-30980.html

The report paraphrases his explanation: "some sites use more HTML, some sites use less, it is a design thing, not a content thing." https://www.seroundtable.com/google-code-to-text-ratio-algorithm-25503.html. **Myth/contested:** "code-to-text ratio is a ranking factor".
- **Documented, Google page experience** (last updated 2026-09-22): "Our core ranking systems look at a variety of signals that align with overall page experience." and "they can make your website more satisfying to use, which is generally aligned with what our ranking systems seek to reward." https://developers.google.com/search/docs/appearance/page-experience

## Conflicts between sources

1. **WordPress vs Google on permalinks and ranking.** The 7.1 Permalinks screen says including `%postname%` "can help your posts rank higher in search engines". Google says URL-path keywords "have hardly any effect beyond appearing in breadcrumbs". Teach the Google line; give readability as the reason for Post name.
2. **Studio platforms.** The Studio page offers Linux downloads but says "Point-and-click local site management on macOS and Windows." It's unclear whether Linux gets the desktop app or only the CLI. Keep Local as the default for all three OSs.
3. **AVIF timeline.** The 6.5 dev note says AVIF depends on the server's image library. The 7.1 release post says 7.1 "includes native support for AVIF". The 7.1 dev note explains it: client-side processing lets hosts without PHP AVIF support accept AVIF, but only in supporting browsers.
4. **`lastmod` vs "significant update".** WordPress core's sitemap `lastmod` follows `post_modified_gmt`, which changes on any save. Google wants `lastmod` to reflect "the last significant update" and uses it only if "consistently and verifiably" accurate. Practical advice: don't re-save old posts just to look fresh.
5. **Blogger export wording.** The importer readme says "Settings->Other ... Export Blog"; Blogger Help says "Back up content" / Google Takeout.
6. **Wix redirects:** automatic for pages, manual for blog posts, in the same help article. Easy to misreport as "Wix redirects automatically".
7. **Course outline vs brief, Path B.** `seo-101/course-outline.md` §3 calls Path B "the course's free practice site (a WordPress test site; set-up guide in Lesson 1.8)". ## Hands-on ideas (free only)

- **Outline check:** paste a messy draft (bold lines as fake headings, an H4 used "because it's smaller"); fix it in Document Overview → Outline until no "(Incorrect heading level)" shows; restyle with typography or block CSS instead.
- **Break-it lab (page builder), no paid builder needed:** in Playground, build a page whose "headings" are styled paragraphs and whose real headings are used for styling, with a full-size 4000 px hero, three autoplay embeds and a large Custom HTML block. Compare its page outline and page weight with the clean version, using DevTools Network (no Lighthouse run unless asked) and View Source counts of `<h1>`–`<h6>`. Optional extension for learners who choose it: install the free Elementor plugin from wordpress.org in Playground and compare View Source sizes. (A suggestion; not tested.)
- **Slug-change test:** publish a post, change its slug, then visit the old URL and see the 301. Repeat with a **page** and see the 404. Repeat with a **draft** that you then publish (no old slug stored). Record the results in the redirects table from WordPress 101 M05.L02.
- **Archive audit:** open `/wp-sitemap.xml` on the practice site; list each tag archive and its post count; apply the tag rule; decide `noindex` per tag; view source on one archive to see that core adds no `noindex`.
- **Image check:** upload a 4000 px phone photo; confirm the `-scaled` 2560 copy and sub-sizes in the uploads folder; compare file sizes between Chrome and Firefox uploads (7.1 client-side processing). Then add alt text in the block vs the Media Library and see which wins where.
- **Shopify/Wix desk exercise (no account needed):** given screenshots or a description, predict what happens to the old URL after a slug change on each platform, then check against the help-page quotes above.
- **Playground durability drill:** make a Playground, check it shows **Autosaved**, use **Store permanently**, then **Download as .zip** and restore it with **Import zip**.
